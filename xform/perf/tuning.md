# 批量仿射变换：块宽推导、扫描与验收

测量环境（本机实测，非假设）：

| 参数 | 值 | 来源 |
|---|---|---|
| CPU | Intel i7-13620H（Raptor Lake，WSL2） | `/proc/cpuinfo` |
| 缓存行 | **64 B** | `sysfs .../cache/index0/coherency_line_size` |
| L1d | 48 KiB/核，12 路 × 64 组 | sysfs |
| L2 | 1.25 MiB/核，10 路 | sysfs |
| L3 | 24 MiB 共享，12 路 | sysfs |
| 编译器 | gcc 15.2.0，`-O2 -std=c11`（未开 fast-math） | — |
| 单核有效带宽墙 | **24.7 GB/s**，1.29 ns/点（纯流式 16B 读+16B 写） | `bench/bw.c` |

数据形态：每个点两个 `double`（x,y），有效载荷 16 B。稠密布局 `stride=16`，
稀疏布局 `stride=64`（每点独占一条缓存行）。

## 1. 块宽区间的推导（从缓存行和带宽出发，不拍脑袋）

记块宽为 w（点/块），单块内存占用 `C = w × stride`。

**下界（缓存行侧）—— w ≥ 64（稀疏）/ w ≥ 4（稠密），统一取 64。**

- 一条缓存行 64 B。块宽必须以“整数条缓存行”为单位，否则每条边界缓存行都
  出现半行取用，有效带宽按比例打折。稠密时一行装 4 点，w 是 4 的倍数即行对齐；
  稀疏时一行只装 1 点，**w 本身就等于占用的缓存行数**。
- 循环与分块簿记开销（每块一次边界计算、分支、指针步进）要被摊薄到
  可忽略：实测 w ≤ 16 时（dense/nan）每点耗时比平台值高 20%–140%，
  说明几十个点的块仍被簿记开销主导。取 w=64 点（=64 条缓存行=4 KiB）
  作为统一下界，簿记/点已降到 1/64。

**上界（L1d 容量侧）—— w ≤ 768（稀疏）；结合 L2 与 TLB 放到 4096。**

- 块的工作集应留在 L1d（48 KiB）内，才能保证同一块“读—算—写”不被驱逐到
  下层缓存。稀疏布局最吃容量：`w × 64 B ≤ 48 KiB ⇒ w ≤ 768`。
  稠密布局对应 `w ≤ 3072`。
- L1d 是 12 路组相联：4 KiB 块 = 64 行 × 64 B，若按 4 KiB 对齐，恰好
  每个组落 1 行，12 路全无冲突；这正是取 256 点（稠密 4 KiB）的相联依据。
- 再往上，L2（1.25 MiB）允许稠密 w ≤ 81920、稀疏 w ≤ 20480；但 L1 失配后
  延迟从 ~4 周期升到 ~14 周期。另考虑 DTLB（4 KiB 页，64 项 L1 dTLB）：
  块覆盖超过 64 个页（稠密 w=16384）开始吃二级 TLB。**取上界 4096 点**
  （稠密 64 KiB，已超 L1 但远在 L2 内、仅 16 个页；稀疏 256 KiB，仍在 L2 内）。

**结论：理论有效区间 w ∈ [64, 4096] 点**；在此区间内逐点扫描
（外加 4/8/16/32 与 8192/16384 作为区间外对照），让数据选出最优点。

## 2. 带宽侧的交叉验证

每点固定搬运 32 B（16 B 读 + 16 B 写回），与块宽无关；块宽只决定这些
访问落在哪一级缓存。

- 微基准测得单核带宽墙 24.7 GB/s（1.29 ns/点）。
- long 场景（152.6 MiB，超出 24 MiB L3，必然走 DRAM）最优内核实测
  1.26 ns/点、25.5 GB/s——**已贴在带宽墙上**，说明内核没有多余流量，
  块宽在该场景只能决定“离墙多近”，不能穿墙。
- dense/nan（1.53 MiB）整体落入 L3，局部块在 L1/L2 命中，等效带宽
  66–73 GB/s，每点 0.44–0.48 ns，受的是 L1/L2 延迟与执行吞吐，不是 DRAM。
- sparse（6.1 MiB）同样在 L3，但 48 B/行的空洞使有效载荷率仅 25%，
  实测 22.4–22.9 GB/s，与 long 的 DRAM 带宽几乎相同——**稀疏布局下
  缓存行浪费等效于“免费把数据放到了内存墙上”**，这也是它对块宽不敏感的原因。

## 3. 扫描结果与最优点

每场景 3 轮 × 每块宽 31 次独立测量取中位数（`taskset -c 2` 绑核），
完整数据见 `analysis.md` / `final_*.txt`。下表为三轮中位的摘要
（ns/点，括号内是相对该场景最优值的差距）：

| w | dense | sparse | nan | long |
|---:|---:|---:|---:|---:|
| 16 | 0.530 (+20%) | 1.395 (~0%) | 0.526 (+19%) | 1.310 (+4%) |
| 64 | 0.514 (+17%) | 1.433 (+3%) | 0.516 (+17%) | 1.322 (+5%) |
| 128 | 0.470 (+7%) | 1.411 (+1%) | 0.472 (+7%) | 1.287 (+3%) |
| **256** | **0.455 (+3%)** | **1.403 (~0%)** | **0.455 (+3%)** | **1.317 (+5%)** |
| 512 | 0.447 (+2%) | 1.423 (+2%) | 0.455 (+3%) | 1.303 (+4%) |
| 1024 | 0.445 (+1%) | 1.418 (+2%) | 0.445 (+1%) | 1.271 (+1%) |
| 2048 | 0.443 (~0%) | 1.419 (+2%) | 0.443 (~0%) | **1.256 (best)** |
| 4096 | 0.442 (~0%) | 1.432 (+3%) | 0.442 (~0%) | 1.277 (+2%) |
| 16384（区间外） | 0.441 (best) | 1.424 (+2%) | 0.442 (best) | 1.281 (+2%) |

**各场景耗时最小点：dense 16384、sparse 16、nan 16384、long 2048。**
但注意三个事实：

1. dense/nan 的最优点 16384 对 256 的领先只有 3%，且 16384 已超出 L1d
   （稠密块 256 KiB）、跨 64 个页，这个“最优”是 L3 足够大时的平台末端，
   换更大输入就不再成立，不具可移植性。
2. sparse 的 16 与 2048 差异 <2%，整条曲线在测量噪声内（±5%），
   不存在有意义的最优点——它被缓存行有效载荷率锁死。
3. long 的 2048 对 256 的领先约 5%，同样在 WSL2 调度噪声边缘。

**工程取点：w = 256（默认值，已写入 `xform_batch.c`）。** 为什么是它：

- 它是推导区间 [64, 4096] 内**唯一同时满足**下列条件的点：稠密块恰为
  4 KiB（64 条缓存行、12 路组相联下每组 1 行、零缓存集冲突、单页内）；
  稀疏块 16 KiB，仍是 L1d(48 KiB) 的 1/3，工作集确定留在 L1。
- 四个场景全部落在各自平台区内，最坏代价（long +5%、dense/nan +3%）
  远小于块宽失配时 20%–140% 的惩罚；即“不是任何单场景的极值，但是
  全场景的最小后悔值”。
- 若部署方确定输入始终是超大 DRAM 驻留数组，可把默认值上调到 1024–2048；
  本库保留 `w` 参数而不是写死，正是为此。API 传 `w=0` 取默认 256。

## 4. 四场景验收（默认 w=256，31 次中位）

耗时为一次完整调用的墙钟中位数；峰值内存取 `VmHWM` 差值并由
`--wrap` 计数器交叉核对。

| 场景 | n / stride | 输入大小 | 峰值内存（归因） | 峰值/输入 | 耗时 | 块宽 |
|---|---|---:|---:|---:|---:|---:|
| 稀疏 sparse | 100000 / 64B | 6.10 MiB | 6.36 MiB | **1.041** | **0.143 ms** | 256 |
| 稠密 dense | 100000 / 16B | 1.53 MiB | 1.78 MiB | **1.165** | **0.048 ms** | 256 |
| 含 NaN nan | 100000 / 16B | 1.53 MiB | 1.78 MiB | **1.165** | **0.045 ms** | 256 |
| 超长 long | 10⁷ / 16B | 152.59 MiB | 152.84 MiB | **1.002** | **15.02 ms** | 256 |

- 峰值/输入全部 ≤ **1.2**（dense/nan 的 1.165 中含基准进程自身的
  分配器记账与页取整，随输入增大收敛到 1.00，long 已证）。
- 十万点三场景耗时 0.045–0.143 ms，全部 ≪ **30 ms** 预算（余量 200 倍以上）。
- 对照（二次拷贝）实现同机实测峰值/输入 = **2.00–2.21**，即原地方案
  省掉了整整一份输出数组；long 场景下二次拷贝内核 19.8 ms vs 原地 15.0 ms，
  多出的 48 B/点流量（+50%）在 DRAM 墙上直接变成 32% 的耗时差。
- NaN 场景与稠密场景曲线几乎重合：IEEE 754 的 NaN 经乘/加自然传播，
  内核无任何 NaN 分支，逐位校验（含 NaN 位置）通过。

## 5. “没有第二次拷贝”的依据（四层证据）

1. **接口层**：`xform_apply_batch_strided(base, n, stride, w)` 只接收一个
   缓冲区指针，没有输出参数；函数原型上就不存在第二份数组的存放位置。
2. **实现层**：`src/xform_batch.c` 全文无 `malloc/calloc/realloc/
   aligned_alloc/posix_memalign`，无 `memcpy/memmove/mempcpy`；每点
   经 `__builtin_memcpy` 做 8 B 标量装载与写回（编译后是单条 `movdqu`/
   `movups` 指令），地址始终是 `base + i*stride` 同一位置，先读后写。
3. **链接层（运行时拦截）**：基准程序以 `-Wl,--wrap=` 拦截全部五个分配
   符号与三个拷贝符号（配合 `-fno-builtin` 阻止内置绕过）。变换期间
   实测 `alloc_calls=0 alloc_bytes=0 copy_calls=0 copy_bytes=0`
   （见 `mem_*.txt` 与每张扫描表最后两列）。
4. **指令层**：`perf/kernel.asm` 为内核反汇编，全文 `call` 指令数 = 0；
   内循环仅 7 条指令——`movdqu` 读、两次 `punpck` 拆 x/y、`mulpd/addpd`
   各两条完成仿射、`movups` 写回同一地址。无任何库调用可产生拷贝。

数值正确性另由 `bench verify` 保证：14 个块宽 × 4 场景全部与逐点
`xform_apply` 参考实现逐位一致（NaN 以 `isnan` 比较），`make -C xform test`
的 9848 项断言全过。

## 6. 复现方式

```sh
make -C xform test                       # 单元测试（含 NaN、稀疏步长、末块）
make -C xform bench
for s in dense sparse nan long; do
  ./xform/build/bench verify $s          # 逐位校验
  ./xform/build/bench mem    $s          # 峰值内存 + wrap 计数器
  ./xform/build/bench sweep  $s 31       # 块宽扫描
done
gcc -O2 xform/bench/bw.c -o /tmp/bw && taskset -c 2 /tmp/bw   # 带宽墙
```
